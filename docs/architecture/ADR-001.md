# ARCH-001 — ADR-001: arquitetura Android

Estado: proposta fundamentada em documentação; compatibilidade integrada ainda não testada.

## Decisão proposta

Adotar Kotlin 2.x e Jetpack Compose no leitor, Material 3 como base de interação e acessibilidade, com design system próprio. Usar Chaquopy exclusivamente no aplicativo executor, mantendo UID separado. Java permanece opção para componentes interoperáveis quando justificar menor complexidade. Não incorporar runtime Python ao leitor.

Módulos iniciais: :reader (APK), :executor (APK), :protocol (biblioteca de contratos IPC sem segredos). Separar responsabilidades de UI, domínio, persistência e catálogo por pacotes inicialmente; extrair módulos quando houver benefício demonstrado. Fluxo de estado unidirecional, ViewModels e operações assíncronas com cancelamento. Não colocar lógica de rede ou execução diretamente em composables.

## Compatibilidade documental

Consulta em 26/11/2026:
- https://chaquo.com/chaquopy/doc/current/versions.html — Chaquopy 17.2 suporta AGP 7.3–9.5, Python 3.10–3.15 e API mínima 24.
- https://chaquo.com/chaquopy/doc/current/android.html — configuração Gradle, ABIs e limitações da biblioteca padrão; tkinter e turtle indisponíveis.
- https://chaquo.com/chaquopy/doc/current/changelog.html — versão 17.2.0; suporte a páginas de 16 KB introduzido na série 17, recomendação de Python 3.13+ para compatibilidade de wheels.
- https://developer.android.com/jetpack/androidx/releases/compose-kotlin — Kotlin 2.0+ usa plugin Compose Compiler.
- https://developer.android.com/develop/ui/compose/bom — BOM para coordenar bibliotecas Compose; compilador segue versão Kotlin, não BOM.

Candidato inicial: Chaquopy 17.2.0, Python 3.13, arm64-v8a e x86_64. API 24 é piso do runtime, não compromisso final de suporte: dependências AndroidX podem elevar o mínimo. Fixar AGP, Gradle, JDK, Kotlin, BOM, SDK e versões transitivas após verificação conjunta de documentação e build. Python de build deve ter mesma versão major/minor do runtime. Evitar versões preview sem necessidade.

## Segurança e distribuição

Respeitar SECURITY-001. Leitor é único cliente de rede; executor sem INTERNET e sem acesso ao armazenamento privado do leitor. IPC autenticado por assinatura e UID, protocolo versionado e sessões limitadas. A separação em processos não substitui separação por UID. Não prometer sandbox absoluta.

Biblioteca: adaptador para catálogo existente em desenvolvimento e contrato de produção autenticado por manifesto assinado; sem fallback inseguro em release. Definir ADR separado sobre publicação, rotação e rollback. Não alterar biblioteca nesta etapa.

Preservar identidade de assinatura e compatibilidade de atualização como objetivos, não garantias. Usar IDs de aplicação distintos para protótipos instaláveis lado a lado; validar migração antes de retomar IDs de produção. Assinatura de distribuição fora da CI pública.

## Interface

Glassmorphism com paleta verde, preto, branco e cinza. Efeitos de iluminação e transparência com fallback sem blur real; avaliar contraste, desempenho, acessibilidade e escalas de texto. Não impor Compose ao código gráfico do estudante; toolkit de GUI Python é decisão independente, retomada após console e isolamento homologados.

## Experimento ARCH-002

1. Criar build mínimo com versões fixadas e wrapper verificado, CI sem segredos, ações fixadas por SHA.
2. Compilar leitor Compose e executor Chaquopy separados, inspecionar manifests finais e ABIs.
3. Instalar ambos em emuladores, testar IPC autorizado e rejeição de cliente não autorizado, executar expressão Python e retorno ao leitor sem travamento.
4. Testar ausência de acesso de rede no executor e recuperação após falha. Validar ARM64 em dispositivo ou ambiente adequado, incluindo páginas de 16 KB antes de distribuição.
5. Registrar resultados, versões, limitações, licenças de dependências e decisão final. Nenhum APK de produção ou chave permanente neste experimento.

## Alternativas

Java e Views: menor migração de código mas maior esforço para novo design. Compose no leitor e executor Java: opção compatível com a separação de responsabilidades. Outros runtimes Python: exigiriam reavaliação de empacotamento, compatibilidade e isolamento; não são prioridade sem evidência de limitação impeditiva.

Licença do projeto ainda pendente; não presumir compatibilidade jurídica das dependências nem reutilizar código de terceiros sem revisão.

## DISTRIBUTION-001 — Pythoteca Suite

Modelo preferencial aprovado pela responsável pelo projeto, condicionado à homologação. Acrescentar módulo :installer independente, sem INTERNET, contendo APKs previamente assinados do leitor e executor. Manter APKs individuais para instalação manual. Não confundir APK único de distribuição com UID único de execução.

Investigar PackageInstaller com sessões multi-package atômicas (API 29+), consentimento explícito, restrições de fontes externas e fabricantes. Para API 24–28 avaliar instalação manual ou sequencial, sem alegar atomicidade. Não definir suporte mínimo final antes dos testes. Referência a verificar: https://developer.android.com/reference/android/content/pm/PackageInstaller.SessionParams#setMultiPackage()

### T13 — Comprometimento do instalador e das dependências

Requisito complementar a SECURITY-001: instalador dedicado com escopo fechado, sem APKs externos, URLs arbitrárias ou componentes exportados desnecessários. Verificar hashes, certificados esperados, nomes de pacote, versões, ABI e compatibilidade IPC antes de abrir sessões. Manifesto de distribuição protegido pela assinatura do instalador; validar também identidade do próprio instalador por canal confiável. Não confiar somente em hashes fornecidos pelo mesmo pacote comprometido. Não incluir chaves privadas. Respeitar consentimento e política de instalação do Android; rejeitar downgrade e incompatibilidades. Limpar sessões e temporários em falhas. Leitor autentica executor independentemente após instalação.

### Homologação

Testar instalação limpa, atualização conjunta, componentes já instalados, assinatura divergente, APK adulterado, incompatibilidade, cancelamento, falha de uma sessão filha, recuperação e remoção do instalador sem afetar componentes. Validar preservação de dados e identidade de assinatura em atualização. Testar comportamento em dispositivos reais e versões Android suportadas. Não solicitar permissão de instalação no leitor ou executor. Avaliar política Play Store separadamente se esse canal for adotado.

Assinar componentes antes de montar e assinar a Suite, em pipeline confiável separado da CI pública. Distribuir somente após verificar os três artefatos. Nenhuma implementação ou garantia de instalação silenciosa nesta etapa.
